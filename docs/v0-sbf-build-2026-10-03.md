# Isolated V0 SBF builds, 2026-10-03

The root `npm run build` command now runs [`scripts/build-v0-sbf.sh`](../scripts/build-v0-sbf.sh). It succeeds only after all three V0 programs produce valid entrypoint-bearing BPF ELF artifacts. The former `cargo build-sbf || cargo build` fallback has been removed: a successful host build is not a deployable Solana build.

## Why the programs must be built separately

`basket_factory` depends on `basket` and `whitelist` with the `cpi` feature, which enables `no-entrypoint`. A workspace SBF build can unify these features and write tiny dependency `.so` files over the standalone program outputs. Devnet preflight caught an 896-byte no-entrypoint artifact during this session, before that artifact was submitted.

The wrapper invokes the SBF compiler sequentially with each explicit program manifest and a separate output directory:

| Manifest | Isolated output | Promoted artifact |
|---|---|---|
| `programs/whitelist/Cargo.toml` | `target/xstocks-sbf/whitelist` | `target/deploy/whitelist.so` |
| `programs/basket/Cargo.toml` | `target/xstocks-sbf/basket` | `target/deploy/basket.so` |
| `programs/basket_factory/Cargo.toml` | `target/xstocks-sbf/basket_factory` | `target/deploy/basket_factory.so` |

The script never uses `--workspace`. Caller flags are forwarded before the fixed manifest/output arguments. Workspace, package-selection, manifest/output overrides and the `--` forwarding separator are rejected because they could defeat isolation.

Each artifact must be larger than 4,096 bytes, have ELF magic, 64-bit little-endian class, ET_DYN type, legacy EM_BPF machine value 247 or modern EM_SBPF value 263, and a nonzero entrypoint. Validation uses Python's standard library and prints the size, entrypoint and SHA-256. This checks the binary envelope; it does not replace SBF execution, source reproducibility or deployed-byte attestation.

An old named `.so` is removed from its isolated build directory before that program's invocation, so a builder returning success without emitting a binary cannot reuse stale output. Other outputs and all keypair files are preserved. Only after **all three** builds and validations succeed does the wrapper promote the three named `.so` files. It never copies a wildcard directory or generated keypairs. An empty lock directory prevents concurrent wrapper builds; a stale lock should be removed only after checking that no build is running.

## Current toolchain command

The current session uses Agave 4.3's `cargo-build-sbf`, platform-tools v1.56 and its Rust 1.89 compiler. The root task verified manual isolated invocations with the following binary/tool options. The new wrapper uses the same command shape:

```bash
BASALT_CARGO_BUILD_SBF=/private/tmp/basalt-sbf-toolchain/solana-release/bin/cargo-build-sbf \
RUSTC=/private/tmp/basalt-sbf-toolchain/platform-tools-v1.56/rust/bin/rustc \
PATH="/private/tmp/basalt-sbf-toolchain/platform-tools-v1.56/rust/bin:$PATH" \
npm run build -- \
  --tools-version v1.56 \
  --skip-tools-install \
  --no-rustup-override \
  --offline \
  --arch v0
```

These are the actual local paths for this session, not permanently installed paths. On another machine, set `BASALT_CARGO_BUILD_SBF` to the compatible executable and supply the corresponding compiler environment. The script defaults to `cargo-build-sbf` from the caller's PATH, does not install tools, and preserves the caller's PATH/RUSTC. It does not silently switch compilers or target architectures.

The older `scripts/e2e.sh` comment about platform-tools v1.41 and a version-3 lockfile is historical. See [toolchain readiness](devnet-contract-readiness-2026-10-03.md), [token policy](xstocks-token-policy-decision-2026-10-03.md) and [devnet runtime proof](xstocks-devnet-basket-proof-2026-10-03.md) for current evidence. Final deployed artifact hashes belong to the root deployment record, not the synthetic wrapper tests below.

## Wrapper validation

- `bash -n scripts/build-v0-sbf.sh` passed.
- Fourteen controlled tests passed using a disposable fake compiler and temporary repository outside the canonical build directories.
- Positive cases cover both legacy EM_BPF=247 and modern EM_SBPF=263: three separate invocations in whitelist/basket/factory order, correct forwarded flags and caller RUSTC, three validated named ELF outputs, no keypair promotion.
- Negative cases: 896-byte stub, zero entrypoint, host ELF machine, wrong ELF class, wrong magic, missing output and compiler exit 42. In each case, the command failed and existing deployment artifacts stayed unchanged, including when the third build failed.
- Isolation override cases: `--workspace`, `--manifest-path=...`, `--sbf-out-dir=...`, `--`, and `-pwhitelist` all failed before invoking the compiler.

The tests exercise failure handling and binary validation without parallel compilation or chain transactions. The root task owns the actual current SBF rebuild, source/artifact hashes, deployment and post-deployment runtime proof.

The first actual wrapper invocation correctly preserved existing deployment artifacts but rejected the modern compiler's valid `EM_SBPF=263` header. The validator now accepts both observed Solana ELF machine values (247 and 263); all other header, size and entrypoint checks remain. The root task reruns the actual build after this correction.
