# Managed Basket V2 — Threat Model and Instruction Test Matrix

> Status: design artifact for implementation planning. No V2 instructions or tests are implemented by this document. Scope is the first localnet/devnet proof described in `managed-basket-v2-plan.md`; it is not an audit or a mainnet approval.

## 1. Scope and security objective

V2 is a separate managed-basket program and account model. V0 accounts and instructions remain immutable. A managed basket has one Token-2022 share mint and one shared vault per constituent. A manager proposes a target-weight version; a distinct guardian approves the exact trade bound; after the notice delay, an RFQ taker can atomically exchange one fixed pair of assets against the vault. The initial proof uses 2–3 project mock mints, fixed constituents, and no arbitrary DEX CPI.

The primary objective is to preserve each holder's claim on the actual vault while permitting a bounded, disclosed manager-directed trade. For constituent `j`, pre-fee redemption entitlement is:

```text
floor(vault_raw_j × holder_shares / total_share_supply)
```

Target weights are a strategy mandate, not the share ledger. A rebalance changes actual vault balances, not share supply. Each holder then has the same fraction of the new actual balances.

## 2. Trust assumptions and limits

| Actor or system | Assumption for the prototype | Consequence if compromised or unavailable |
| --- | --- | --- |
| Solana runtime and Token-2022 program | Runtime execution, account ownership, signatures, and standard token transfer semantics work as specified. | A runtime or canonical token-program failure is outside the basket program's recovery boundary. |
| Basket program | The reviewed deployed binary enforces the invariants below. It remains upgradeable under the recorded program governance. | A malicious or vulnerable upgrade can bypass every program invariant; manager/guardian checks do not constrain the upgrade authority. |
| Manager | Authorized to propose policy changes, but may be malicious or compromised. It cannot sign as the vault PDA or select arbitrary recipients. | Can propose harmful but otherwise valid target weights and attempt to persuade a guardian to approve a poor trade. |
| Guardian | A distinct, independently controlled key supplies a minimum-output bound and approves a final hash binding it to the manager's immutable proposal. | Guardian approval is the prototype's price-policy trust assumption. A guardian can approve a structurally valid but economically poor limit. This is not an objective fair-price proof. |
| RFQ taker | Adversarial; may submit wrong accounts, stale fills, or fail to deliver output. It must sign its incoming token transfer. | Invalid or incomplete settlement must fail atomically. The taker can decline to fill, so execution is not guaranteed. |
| Token issuer / mint authorities | First release uses simple project mock mints with no hostile extensions or mutable transfer behavior. | A real issuer can pause transfers or change hook/scaled-amount configuration where the relevant authority exists. This can stop redemption or alter displayed NAV independently of Basalt. |
| Backend, indexer, UI, RPC quote | Read-only and untrusted for authorization, balances, price bounds, proposal state, and redemption. | Stale or false data may mislead a user, but cannot authorize a trade or block an on-chain redeem. |

**Price-bound limitation:** the guardian signs an exact bound, not an oracle attestation. A positive `min_out` and a notice period prevent neither a guardian-approved bad price nor a colluding manager/guardian. Tests must verify the bound is committed and enforced exactly, and must record this residual trust. Production requires a separately reviewed independent price-bound, auction, or limit-order design before implying best execution.

**RFQ settlement:** the initial fill must use direct, atomic Token-2022 transfers between the canonical vault ATA and the taker's canonical token account. Do not CPI into manager-selected programs. Source spend is capped, destination received is measured from raw balance deltas, and the full approved order either settles in the same transaction or reverts. A future DEX adapter is a separate threat model and gate.

**Redemption liveness:** the program must expose redeem in every V2 lifecycle state without a manager, guardian, proposal, price feed, whitelist, backend, or indexer account. This guarantees only that Basalt adds no such gate. It cannot guarantee a successful underlying transfer if an issuer pauses the mint or a transfer hook rejects the CPI; the first release therefore uses extension-free mocks and makes no unconditional exit claim for issuer-controlled assets.

## 3. Security invariants

1. **Version isolation:** V2 uses new program IDs/seeds and an explicit schema version. It never reinterprets or migrates a V0 `Basket` account.
2. **Single-pool share accounting:** actual raw vault balances and Token-2022 mint supply are the only redemption inputs. Rebalance does not mint, burn, freeze, or transfer share tokens. Checked widened arithmetic and floor rounding must never overdraw a vault.
3. **Authority separation:** manager and guardian keys are distinct. The manager proposes; the guardian approves the exact proposal hash; the taker supplies the counterparty leg; only the basket PDA authorizes movement out of vault ATAs. None of those roles can withdraw to an arbitrary recipient.
4. **Committed fill:** the manager's immutable proposal includes program/basket identity, schema/version, monotonic nonce, pair, exact input amount, target weights, approval deadline, notice duration, and execution-window duration. The guardian supplies minimum output and approves a final hash binding **all** executable terms. Approval cannot be replayed for another basket, version, or fill. It stamps `approved_at`; the program derives `not_before = approved_at + notice_duration` and `expires_at = not_before + execution_window`. It checks all boundaries using the on-chain Clock sysvar, not a client timestamp.
5. **Atomic exchange:** the vault's source debit cannot exceed the approved amount; the taker's input transfer and vault output receipt occur together; post-transfer raw deltas satisfy the approved bound. Every fixed constituent vault must have a positive raw balance immediately before and after fill. Any failed account, signature, transfer, balance, or bound check reverts the whole fill and leaves proposal/execution state unchanged.
6. **Open in-kind exit:** redeem uses current actual balances and remains available before proposal, during the notice period, after fill, after cancel/expiry, when the manager or guardian is unavailable, and when indexer/NAV data are stale. It is not priced by target weights or an oracle.
7. **Proposal is not execution:** target-version state advances only in the same successful fill transaction; proposal, approval, cancel, expiry, and execution are separate observable states/events. UI or indexer data cannot mark a proposal as current holdings.
8. **Extension boundary:** first-release assets and share mints reject unsupported Token-2022 extensions. Any future allowlist expansion needs instruction-level extension fixtures, exact raw delta accounting, mutable-authority analysis, and a revised redemption-liveness statement.
9. **Governance boundary:** manager and guardian cannot change program code, extension policy, fee caps, fixed constituent list, or upgrade authority. Mainnet is blocked until actual autonomous 2-of-3 multisig and time-lock state is verified; a written target policy is not evidence of deployed governance.

## 4. Threat register

| ID / severity | Threat | Required control and residual risk |
| --- | --- | --- |
| T1 / Critical | Manager or a compromised manager tries to withdraw assets, redirect a vault transfer, change the constituent set, or execute an unapproved trade. | No manager signer privilege over vault; no arbitrary CPI; fixed asset set; exact proposal hash and trade accounts; tests assert unauthorized direct transfer/update is impossible. A valid guardian-approved proposal can still reduce value. |
| T2 / Critical | Guardian approves a zero, overly permissive, stale, or manipulated price bound. | Reject zero/invalid bounds; bind approval to exact pair, input, output floor, basket/version/nonce, and expiry. On-chain code can enforce the signed floor but cannot identify a bad fair-value estimate without an independent price source. Guardian trust is an explicit prototype assumption. |
| T3 / High | Malicious RFQ taker substitutes token accounts, pays the wrong mint, underpays, front-runs a stale fill, or attempts partial settlement. | Canonical Token-2022 program/mint/ATA/owner checks; taker signature; exact input and minimum raw output; delay/expiry; one atomic full fill; raw pre/post delta checks. Taker can always refuse service. |
| T4 / High | Proposal replay or stale-state execution after a prior fill, cancel, expiry, manager rotation, or newer target version. | Domain-separated proposal hash, monotonic nonce/version, one-way lifecycle transitions, fill-once flag; reject cross-basket and prior-version replay. |
| T5 / High | User redeem or another operation changes vault balances after proposal, making quoted amounts stale or reducing a constituent to zero. | Fill re-reads live balances, re-checks source capacity, and requires all fixed vaults remain positive before and after; it must fail without state changes if any condition is false. Redeem always wins; manager/guardian cannot lock it to preserve a quote. Manager may cancel/re-propose under policy. |
| T6 / High | Partial fill or multi-transaction execution strands a basket, blocks exits, or reuses stale leg amounts. | First release supports full single-pair fill in one transaction only. Partial fill is rejected. Multi-leg/multi-tx is out of scope until a separate state machine, mint policy, expiry recovery, and redeem-at-every-stage suite are specified. |
| T7 / Critical for supported asset claims | Issuer pause, permanent delegate, transfer hook, confidential transfer, or transfer fee invalidates vault control/accounting or blocks redemption. | Fail-closed extension admission for prototype. Test relevant extensions and mutable authorities. Do not claim unconditional exit for a token whose issuer can prevent its transfer. |
| T8 / High | Token-2022 share mint has freeze, permanent-delegate, transfer-fee, hook, or confidential behavior that changes holder transfer/redemption assumptions. | Create share mint with exact reviewed configuration: only PDA mint authority, no freeze authority, and no unreviewed extensions. Verify mint account after initialization; tampered/substituted mint must fail every instruction. |
| T8a / Medium | The supply-one identity NFT is reminted, its metadata is silently edited, or its transferee is treated as manager. | Zero decimals; verify supply exactly one; revoke further mint and metadata-update authority after creation. Manager role and fee recipient are separate V2 state, never inferred from NFT ownership. |
| T9 / Critical release gate | Single-key or manager-controlled upgrade can replace program logic and seize/redirect assets. | Upgrade authority must be independent autonomous 2-of-3 with configured delay and fresh on-chain evidence before mainnet. Local governance rehearsal is not production proof. |
| T10 / Medium | Indexer reports a proposal as executed, reports stale target/holdings, or misses events. | Reconstruct status from confirmed program events plus account/balance reconciliation; include version, signature, slot, actual raw deltas. Backend stays read-only. On-chain redeem builders fetch canonical accounts directly. |

## 5. Instruction-level test matrix

These are acceptance tests to implement with ProgramTest/LiteSVM or equivalent instruction execution. Host-only arithmetic tests do not satisfy the matrix. “No state change” includes token balances, mint supply, proposal nonce/status, target version, and emitted successful-execution events.

| ID | Instruction / boundary | Scenario | Expected result |
| --- | --- | --- | --- |
| C-01 | `create_managed_basket` | Valid manager, distinct guardian, fixed 2–3 allowed mock mints, positive weights summing to 10,000, atomic nonzero seed. | Succeeds; creates canonical PDA/vault ATAs/share mint, one initial supply, immutable fees/asset set, version 0. |
| C-02 | `create_managed_basket` | Wrong token program, legacy mint, duplicate/unsupported mint, wrong decimals, wrong mint owner, substituted ATA, nonpositive weight, bad weight sum, invalid fee cap, zero seed. | Fails before durable state/token movement. |
| C-03 | Token-2022 admission | Permanent Delegate, Pausable, Transfer Hook, Confidential Transfer, Transfer Fee, non-Initialized DefaultAccountState, unknown extension. | Fails closed for first-release policy. If extension support is later proposed, it needs a separate positive/negative fixture suite; this document does not authorize it. |
| C-04 | Share-mint verification | Freeze authority, Permanent Delegate, Transfer Fee, Transfer Hook, wrong decimals, wrong mint authority, or substituted mint. | Creation or all subsequent operations fail; accepted share mint has only canonical PDA as mint authority and no freeze authority/unreviewed extension. |
| C-05 | Identity NFT verification | Create, try a second mint, try metadata edit, transfer the NFT, then propose as the transferee. | Exactly one zero-decimal NFT remains; further mint/edit fails; NFT transfer alone grants no proposal, fee or redeem authority. |
| S-01 | `mint_in_kind` | Two independent holders deposit in the live actual-vault ratio before or while proposal is pending. | Succeeds under the documented fee/tolerance rule; both holders' shares join one common supply. No dependence on backend or target-weight quote. |
| S-02 | `mint_in_kind` | Wrong holder ATA, wrong vault/mint order, stale supplied balances, non-proportional deposit, paused-new-mint state if retained in V2, unsupported extension or unexpected transfer delta. | Fails atomically; no partial deposit or share mint. |
| S-03 | Share math property | Deterministic randomized sequences of seed, mint, fee accrual, rebalance, partial redeem, full redeem over 2–20 raw-balance vectors and boundary values. | Every entitlement uses live raw balances; checked arithmetic; floors never overdraw; rebalance leaves supply unchanged; aggregate outputs never exceed vault balances. |
| R-01 | `redeem_in_kind` | Holder redeems before proposal, after proposal, at the notice boundary, after fill, after cancel/expiry, and with manager/guardian unavailable. | Succeeds permissionlessly from live raw vault balances; no manager/guardian/price/backend/whitelist/proposal-status account is required. |
| R-02 | `redeem_in_kind` | Wrong share mint, holder ATA owner/mint, vault ATA, token program; zero/excess shares; zero supply; max arithmetic values; rounding dust. | Invalid accounts/amounts fail atomically; valid amounts floor safely; no constituent is overdrawn. |
| R-03 | `redeem_in_kind` with issuer-controlled mint | Mock a mint pause or hook rejection after basket creation. | Token transfer CPI may fail; test documents this external liveness limit and confirms there is no Basalt manager/oracle gate. Such assets cannot be described as having unconditional exit. |
| P-01 | `propose_rebalance` | Manager proposes a valid fixed-pair trade and new positive target weights summing to 10,000. | Succeeds once; records immutable proposal terms, pair, exact input, reason/target version, nonce, proposal time, approval deadline, notice duration and execution-window duration. Minimum output is supplied only at guardian approval. |
| P-02 | `propose_rebalance` | Non-manager signer; manager equals guardian; unsupported/additional constituent; duplicate pair; zero/max-overflow amount; invalid target weights; zero/too-short notice; execution window no longer than notice; arithmetic overflow; proposal already pending; altered mandate/fee. | Fails without state change. |
| P-03 | Proposal hash / replay | Copy valid proposal bytes to another basket, old target version, incremented nonce, changed pair, amount, min output, target weights, manager, approval deadline, notice duration or execution-window duration. | Hash/account validation rejects every mutation and cross-basket replay. |
| A-01 | `approve_price_bound` | Distinct guardian approves exact still-pending proposal hash before its approval deadline. | Succeeds once; approval records exact bounds and `approved_at`, then derives `not_before` and `expires_at`. Approval time starts the public notice delay; bounds and derived execution window cannot be silently edited. |
| A-02 | `approve_price_bound` | Manager/non-guardian, same key as manager, mismatched hash or nonce, zero min output, approval after approval deadline/cancel/fill, second conflicting approval, derived expiry overflow. | Fails; no approved state. |
| A-03 | Guardian-price residual | Guardian signs a structurally valid but economically poor positive floor. | Program enforces that exact floor; test and docs must show this can still execute. Do not claim it detects a manipulated fair price until an independent price-control mechanism exists. |
| X-01 | `fill_rebalance` | Correct taker signs input token transfer; exact canonical pair/accounts; sufficient live vault source; fill after delay and before expiry; output meets bound. | Succeeds atomically; only the approved vault ATA pair changes; source debit is within cap, destination raw delta meets min output, share supply is identical, target version advances once, event includes actual deltas. |
| X-02 | `fill_rebalance` | Fill one slot/time-unit before delay measured from guardian approval; at earliest allowed boundary; at execution-expiry boundary; after expiry. | Early/expired fills fail. Boundary behavior matches the single on-chain Clock policy selected in the normative spec; client wall clock is irrelevant. |
| X-03 | `fill_rebalance` | Wrong/unsigned taker, wrong input/output mint, wrong token program, wrong vault/taker ATA owner, aliased accounts, duplicate/extra writable accounts, substituted basket/share mint. | Fails atomically; unrelated vaults and user accounts remain unchanged. |
| X-04 | `fill_rebalance` | Taker sends no output, less than min output, output to wrong account, or a transfer-fee/hook fixture makes actual destination delta smaller than expected. | Fails atomically; both token legs roll back; proposal remains pending and can later expire/cancel. |
| X-05 | `fill_rebalance` | Attempt to spend more than approved input, fill only a partial input, reuse a filled proposal, use an old proposal after newer version, or fill twice. | Fails atomically; only one full fill can advance a version. |
| X-06 | Malicious CPI / route | Pass a fake or manager-selected executable program, malicious route instruction, arbitrary writable vault account, or account claiming it can sign as the vault. | No arbitrary CPI path exists in first release; unsupported accounts are rejected. The basket program remains the only signer for vault outflow. |
| X-07 | Race with redemption | Holder redeems after proposal/approval, leaving less source balance than the approved trade amount or zero raw balance in any fixed constituent; then taker attempts fill. | Fill safely fails with no state change; holder's redeem remains final. A new proposal is required; stale signed limits are not silently resized. |
| X-08 | Positive vault balance | Before fill, source balance equals the proposed debit; after the hypothetical exchange, one fixed constituent would reach zero; separately, any fixed constituent is already zero before fill. | Both fills fail atomically. Valid fill leaves each fixed constituent vault with at least one raw unit after all transfers. |
| X-09 | Trade result vs target | Fill produces actual holdings that differ from target weights due to price movement or allowed output above floor. | Event and read model report actual raw balances/deltas separately from target weights; no test/UI may claim exact target realization without evidence. |
| Q-01 | cancel / expire | Guardian cancels a pending or approved proposal; anyone expires an unapproved proposal at its approval deadline or an approved proposal at its derived execution expiry; try a second terminal transition or fill afterward. | Each valid terminal transition succeeds once; subsequent transition/fill fails. Neither action changes vault or share balances. |
| M-01 | Manager rotation | Current manager nominates new manager; candidate accepts; test same-key guardian collision, wrong candidate, replay, direct overwrite, and actions by old manager afterward. | Two-step rotation only; roles remain distinct; old key loses proposal rights after acceptance. Guardian rotation is separately governance-controlled. |
| G-01 | Governance boundary | Manager or guardian attempts to update fixed assets/fees/extension policy, withdraw, change program authority or invoke an upgrade path. | No such permission exists. Ordinary basket roles cannot mutate program/governance state. |
| G-02 | Release governance | One signer, manager key, former authority, or early proposal attempts V2 upgrade; then test approved 2-of-3 delayed upgrade in isolated governance rehearsal. | Unauthorized/early upgrade fails; successful rehearsal requires configured threshold and delay. Mainnet acceptance still requires fresh RPC reads of actual multisig, vault and program authorities, program hashes, and time-lock state. |
| I-01 | Events / indexer boundary | Proposal, approval, cancel, expiry, fill; duplicate/replayed event ingestion, missing event, stale indexer snapshot. | On-chain status wins; replay is idempotent; indexer reconciles against accounts and cannot influence instructions or redeem construction. |

## 6. Partial execution and extension gates

The first slice must use a single atomic pair fill. **Partial fills and multi-transaction rebalance are unsupported.** A future implementation must first add a separate lifecycle specification with persisted stage/nonce, bounded live-balance checks, mint policy while the portfolio is in flight, permissionless expiry/recovery, and a redeem test at every stage. Redeem must remain enabled even if every execution stage is abandoned. Solana rollback is transaction-scoped; it does not roll back earlier confirmed transactions.

Before testing any real xStock or widening the token allowlist, cover at minimum:

- `ScaledUiAmountConfig`: all share and vault math stays in raw units; multiplier changes affect display/NAV only and are recorded as data events.
- `TransferFeeConfig`: reject for the first slice, or prove source debit and actual destination credit handling in both mint and redeem. A requested transfer amount is not the received amount.
- `TransferHook`: reject by default; if ever supported, validate the current hook program and required accounts on every path, then test hostile/reconfigured hook behavior. A mutable hook authority is an external liveness dependency.
- `PausableConfig`: reject for unconditional-exit products; simulate issuer pause after admission and show the actual CPI failure. Basalt cannot bypass issuer pause.
- `PermanentDelegate` and `ConfidentialTransferMint`: reject unless a new custody/accounting model is reviewed; a delegate can affect vault assets and confidential balances cannot be reconciled by the current model.
- Account-level default state and unknown extension IDs: reject unless explicitly parsed and tested.

## 7. Exit and release gates

1. No program implementation begins until manager/guardian role rotation, Clock basis and boundaries, notice/expiry length, exact-fill semantics, and acceptable trust in guardian price approval are written normatively.
2. Local proof requires instruction-level tests for all matrix cases, two holders across successful/failed rebalance, full and partial redeem in every lifecycle state, and an atomic taker exchange. Host math tests alone are insufficient.
3. Devnet proof uses only project mock mints, V2 IDs, a small test basket, and recorded actual balances/events. It does not establish xStock compatibility, liquidity, fair pricing, governance, or mainnet readiness.
4. Mainnet remains blocked on independent price/auction design, supported-extension proof, adversarial security review, actual 2-of-3 time-locked upgrade governance with fresh chain evidence, and legal/release review. The current governance document describes a target; it does not prove that target is deployed.
